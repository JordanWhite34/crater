CRATER GOALS AND NEXT STEPS
Updated: August 7, 2026


1. PROJECT PURPOSE

CRATER will turn a single aerial or oblique image of a vehicle into an initial,
explainable battle-damage assessment. The system will identify the vehicle,
locate visible components, estimate visible damage to those components, and use
that evidence to estimate likely operational effects.

The initial product is a research prototype and decision-support tool. It is not
intended to be an operationally validated or fully autonomous BDA system.


2. PRIMARY GOALS

- Build a reusable Python package for vehicle battle-damage assessment within
  the approximately 180-hour IR&D scope.
- Accept a cropped vehicle image as the initial input.
- Determine whether the image is assessable and identify the broad vehicle
  family and view when possible.
- Detect all visible CRATER components:
  - windshield
  - wheel
  - track
  - hull
  - communications system
  - mounted gun
- Classify component damage using discrete damage levels rather than regression:
  - no visible damage
  - possible damage
  - severe visible damage
  - unobservable
- Record supporting visual cues such as deformation, missing material, scorch,
  smoke, flame, and debris.
- Feed component observations into an explainable Bayesian belief network (BBN)
  or equivalent configurable probabilistic reasoning layer.
- Estimate vehicle-level effects such as no effect, damaged, burning,
  immobilized, destroyed, or unknown/needs review.
- Return a structured BDA result containing detections, damage levels,
  confidence, supporting evidence, inferred effects, and limitations.
- Preserve uncertainty by allowing unknown, unobservable, and abstained results.


3. SIMPLE STARTING ARCHITECTURE

Vehicle crop
  -> component detector
  -> detected component crops
  -> damage classifier selected by component group
  -> BBN operational-effect inference
  -> structured JSON BDA result

Starting model choices:

- Component detector: TorchVision Faster R-CNN with a ResNet-50 FPN backbone.
- Damage model: image classification with broad component-group heads:
  - mobility: wheels and tracks
  - structure: hull and windshield
  - mission equipment: communications system and mounted gun
- Operational reasoning: a configurable BBN or noisy-OR model stored separately
  from the perception models.

This architecture is deliberately small. Additional models, segmentation, video
tracking, and more detailed component taxonomies can be added after the initial
end-to-end baseline works.


4. INITIAL SCOPE

Primary vehicle families:

- tracked combat vehicles
- wheeled tactical vehicles
- logistics trucks

Stretch family:

- launcher or artillery vehicles

Primary input:

- one cropped vehicle image
- aerial or oblique viewpoint
- visible-light imagery first

Primary output:

- vehicle family and view
- visible component bounding boxes
- component damage level and evidence
- vehicle-level effect probabilities or scores
- confidence, uncertainty, and limitations
- machine-readable JSON


5. CURRENT DATA STATUS

A cleaned civilian vehicle-parts starter dataset has been prepared from
Carparts-Seg under CC BY 4.0:

- 2,585 training images
- 193 validation images
- 192 test images
- 23 original car-part classes in COCO format
- CRATER transfer labels for windshield, wheel, and a weak hull proxy
- 135 incorrectly empty annotations excluded
- source-grouped splits with no detected source-image overlap
- no dependency on Ultralytics software or licensing

This dataset is useful for learning general component localization, but it cannot
teach the model military tracks, communications equipment, mounted guns, or
military-specific damage. A CRATER-specific military bridge dataset is still
required.


6. NEXT STEPS, IN ORDER

STEP 1 - Freeze the starter taxonomy and annotation rules

- Confirm the six initial component classes listed above.
- Use the four discrete component damage levels listed above.
- Define how partially visible, occluded, ambiguous, and absent components are
  labeled.
- Keep component damage labels separate from vehicle-level operational effects.

Deliverable: final annotation guide and class map.


STEP 2 - Train the civilian component-detection baseline

- Load the cleaned 23-class COCO annotations.
- Train Faster R-CNN/ResNet-50-FPN from pretrained weights.
- Evaluate per-class precision, recall, and average precision on the held-out
  test split.
- Save example overlays and document the training configuration.

Purpose: teach the backbone useful vehicle-part features before military
fine-tuning.

Deliverable: reproducible civilian detector checkpoint and baseline metrics.


STEP 3 - Build the military component dataset

- Collect approximately 200 to 300 licensed or public-domain aerial/oblique
  images across tracked combat, wheeled tactical, and logistics vehicles.
- Start with sources such as DVIDS and other company-approved collections.
- Record the source, license, vehicle family, viewpoint, and image lineage in a
  manifest.
- Draw bounding boxes for every visible instance of the six CRATER components.
- Group related or near-duplicate images before creating train, validation, and
  test splits.
- Review a sample of every class for annotation consistency.

Deliverable: versioned military component dataset with COCO annotations,
license/source manifest, and leakage-safe splits.


STEP 4 - Fine-tune the CRATER component detector

- Replace the civilian prediction head with the six CRATER classes.
- Initialize from the civilian component baseline and fine-tune on the military
  dataset.
- Evaluate results by component, vehicle family, viewpoint, object size, and
  visibility.
- Prioritize recall so important damaged components are not silently missed,
  while using confidence thresholds and review flags for uncertain detections.

Deliverable: six-class military component detector and error-analysis report.


STEP 5 - Create the component-damage dataset and classifiers

- Crop labeled components from damaged and undamaged vehicle imagery.
- Label each usable crop with a damage level and any visible damage cues.
- Train the three broad damage classifiers: mobility, structure, and mission
  equipment.
- Include hard negatives, occlusion, poor resolution, and unobservable examples.
- Evaluate class confusion, calibration, and abstention behavior.

Deliverable: component-group damage checkpoints with calibrated confidence.


STEP 6 - Implement the operational BBN

- Define relationships between component state and mobility, survivability, and
  mission capability.
- Store the rules and priors in editable YAML or another simple configuration.
- Use uncertainty-aware inference such as noisy-OR where appropriate.
- Ensure the result explains which observations influenced each conclusion.
- Use unknown/needs review when the evidence is insufficient.

Deliverable: tested BBN that converts component observations into explainable
vehicle-level effect estimates.


STEP 7 - Integrate and evaluate the end-to-end prototype

- Connect assessability, vehicle-family/view classification, component
  detection, damage classification, and BBN inference.
- Define and validate the BDAResult JSON schema.
- Run held-out end-to-end tests and save visual overlays beside JSON results.
- Measure accuracy, failure modes, inference time, and confidence calibration.
- Build a small demonstration showing successful cases and honest limitations.

Deliverable: reusable vehicle_bda Python package and single-image demo.


STEP 8 - Add edge deployment after the core baseline works

- Export the required models through ONNX.
- Run FP16 TensorRT inference on Jetson hardware.
- Benchmark latency, throughput, memory, power mode, and input resolution.
- Add video decoding and tracking only when needed for the separate edge track.

The Jetson effort should initially be described as an edge BDA-triage baseline.
It should not claim validated vehicle-specific damage classification or
immobilization assessment until those capabilities have been evaluated.


7. IMMEDIATE PRIORITY

The next concrete task is to train the civilian Faster R-CNN component detector
using the cleaned Carparts-Seg package. In parallel with normal project work,
the team should begin assembling and licensing the 200-to-300-image military
bridge dataset, because that dataset is the main dependency for detecting the
final CRATER components.


8. MVP SUCCESS CRITERIA

The initial CRATER prototype is successful when it can:

- process a single vehicle crop end to end;
- detect visible components from the six-class starter taxonomy;
- assign discrete component damage levels with confidence or abstain;
- infer vehicle-level effects through an explainable BBN;
- produce valid JSON and a human-readable visual overlay;
- preserve unknown and unobservable states instead of inventing evidence;
- reproduce its results from documented data splits and model settings; and
- clearly state that its conclusions are prototype estimates rather than
  operationally validated BDA.
